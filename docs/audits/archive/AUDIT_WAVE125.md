## SW arc — what each commit does

### SW1 — Phase 1 (`73eb9389c`)

**Plan**: per design doc §3 Phase 1: install `@tanstack/react-start nitro`, add `tanstackStart()` plugin alongside existing chain, configure SPA mode (`spa: { enabled: true }`), preserve runtime SPA behavior.

**Actual delivery**:

- `npm install @tanstack/react-start@1.167.62 nitro@3.0.260429-beta` — clean install, 0 new vulns, 90 transitive deps added.
- `@tanstack/router-vite-plugin` removed (replaced by tanstackStart's bundled router functionality), `@tanstack/react-router-devtools` bumped 1.166.11 → 1.166.13 to dedup `@tanstack/router-core` (was at 1.168.7 ↔ 1.169.1, manifested as missing `getStylesheetHref` export error).
- `vite.config.mts` — replaced `TanStackRouterVite()` at `plugins[0]` with `tanstackStart({ router: { quoteStyle: "double" } })`. Plugin order constraint per Context7 docs: react vite plugin must come after start vite plugin (we kept react at index 3, tanstackStart at index 0).
- `src/router.ts` — added `getRouter()` factory function alongside existing `export const router`. TanStack Start v1's `start-client-core/hydrateStart.js` imports `getRouter` from `#tanstack-router-entry` (mapped to this file by tanstackStart). Even in SPA mode the hydration entry is bundled, so the export must exist for the import to resolve.
- `src/routeTree.gen.ts` — auto-regenerated, gained TS Register interface for `@tanstack/react-start`.

**Phase 1 deviations from design doc** (documented in commit message):

1. **`spa: { enabled: true }` NOT enabled in Phase 1** — design doc said it preserves SPA behavior. Empirically it triggers a build-time SPA shell prerender that runs React SSR through `__root.tsx`. Our `__root.tsx` uses MainLayout + provider-dependent components mounted in main.tsx at runtime, not in __root. SSR throws `useAppShell must be used within an AppShellProvider`. The schema's `spa.prerender.transform` hardcodes `enabled: true` after user options spread — no config opt-out. Phase 1 omitted the spa: config entirely.
2. **Filter for dev-server + preview-server sub-plugins** — tanstackStart unconditionally adds two middleware plugins that hijack `vite dev` / `vite preview` to load `dist/server/server.js` and run React SSR for every request. Same provider-tree issue as shell prerender. Verified by reading `node_modules/@tanstack/start-plugin-core/dist/esm/vite/{dev,preview}-server-plugin/plugin.js` — no config opt-out. Phase 1 filtered them via the `ssrHijackNames` Set in vite.config.mts.
3. **`appType: "spa"` override** — tanstackStart's `tanstack-start-core:config` plugin sets `appType: "custom"`, which disables Vite's built-in SPA fallback middleware. Override to `"spa"` restored fallback behavior so `vite dev` returns SPA shell HTML for any route.

**SW1 caveat surfaced post-commit** (during SW2 prep): the SW1 commit message claimed "Static dist/ via npx serve: full SPA (GET /login → 10,353 byte HTML)" — but this verification was on a STALE `dist/index.html` left over from a pre-W125 build. After clean `rm -rf dist && npm run build`, the SW1 config produces NO index.html anywhere — Vite 8 environments writes only to `dist/client/assets/` (no top-level HTML), no spa shell prerender runs (filter + no spa.enabled), and the stale `dist/index.html` was a phantom. **Phase 1 in isolation does not produce a static-servable SPA build.** This is what triggered the Phase 2 pull-forward.

### SW2 — Phase 2 (`72e16aa6a`)

**Architecture**:

- **`src/server.ts`** (NEW): minimal `createServerEntry({ fetch(request) { return handler.fetch(request) } })` from `@tanstack/react-start/server-entry`. Used by tanstackStart's prerender + preview-server + dev-server middleware to invoke React SSR.

- **`src/routes/__root.tsx`**: added `ssr: false` flag + new `shellComponent: RootShell` returning the full `<html>` scaffold. The shell renders `<head>` (HeadContent + initial paint CSS), `<body>` (LHCI marker + `<div id="root">{children}</div>` + Scripts). Pre-W125 `index.html` content (theme detection inline script, picsum preconnect, all meta tags, manifest links, font preload anchor) ports to the route's `head: () => ({...})` config which TanStack Router's `<HeadContent />` injects. The existing `RootComponent` (MainLayout + providers) keeps an `import.meta.env.SSR` guard as defense-in-depth.

- **`src/router.ts`**: replaced `context: { auth: undefined!, queryClient: undefined! }` with `context: { auth: SSR_STUB_AUTH, queryClient: SSR_STUB_QUERY_CLIENT }` — stub values that route guards can read without crashing on SSR. App.tsx's `<RouterProvider context={...}>` overrides these with real `useAuth()` values at client mount. `defaultSsr: false` was attempted on the router but the option lives on `RouterConfig` (separate from `RouterConstructorOptions`); the `ssr: false` flag on the root route achieves the equivalent at the route layer.

- **`vite.config.mts`**: re-enabled `spa: { enabled: true }` with `client: { entry: "main.tsx" }` and `server: { entry: "server.ts" }`. Removed the SW1 filter + `appType: "spa"` override (no longer needed; shellComponent makes the shell SSR-safe natively).

- **`scripts/post-build-shell.mjs`** (NEW): post-build HTML processing for `dist/client/_shell.html`, replacing what the `withFontPreload` + `withStrictCspNonce` Vite plugins did pre-W125 via `transformIndexHtml` (that hook does not fire on TanStack Start's React-SSR-rendered shell). Four operations:
  1. Inject CSP nonce placeholders (`<script>` → `<script nonce="__CSP_NONCE__">`) per DEBT-05 strict-dynamic CSP posture.
  2. Inject critical font preload links (`inter-cyrillic-wght-normal-*.woff2`, `outfit-latin-wght-normal-*.woff2`) per W124 SW2 FOIT-reduction.
  3. VITE_LHCI placeholder replacement (LHCI marker visibility CSS + `%VITE_LHCI%` → `"true"`).
  4. Mirror `_shell.html` → `index.html` in same directory for static-serve compat (LHCI staticDistDir, `npx serve -s`).

- **`scripts/run-build.mjs`**: spawns `post-build-shell.mjs` as a fresh node child process at end of build via `await run("node", [path.resolve(process.cwd(), "scripts/post-build-shell.mjs")])`. Earlier alternatives proved unreliable: (a) in-process await broke on Windows when vite's spawned child terminated parent event loop early under `shell: true`, (b) npm pre/post lifecycle hooks (`postbuild`) are not auto-run by `npm run build` since npm 7+. Spawning a fresh node child as the last step gives deterministic execution.

- **`package.json`**: added `build:shell` convenience script for manual re-runs of post-build (e.g. iterating without rebuilding the bundle).

**Phase 2 deferrals to Phase 3 (W126+)**:

- Provider hoisting above `<StartClient />` so `RootComponent` can SSR with the real provider chain. Currently `import.meta.env.SSR` short-circuits `RootComponent` to `null` on SSR — works for SPA shell mode but doesn't help when we want full route SSR for SEO / server-rendered initial state.
- Auth-at-edge (cookie-based session) so `_auth.tsx`, `_admin.tsx`, `_public.tsx` beforeLoad guards see real auth on SSR instead of the stub `{ isAuth: false }` context.
- `<StartClient />` adoption (replace `App.tsx` pattern with the canonical TanStack Start client entry) — requires solving auth context injection without `<RouterProvider context>` prop, possibly via `router.update({ context })` post-hydration.

### SW3 — Storybook fix (`b756a4ffd`)

`npm run build-storybook` initially failed with `[plugin tanstack-start:start-manifest-capture-client-build] Error: multiple entries detected: assets/index-XXX.js`. Storybook's iframe build emits multiple entries (one per story bundle group); the manifest plugin asserts exactly one client entry.

The `.storybook/main.ts` `viteFinal` hook (which already strips `vite-plugin-pwa` since W120 SW8) gets a parallel filter for these specific TanStack Start plugins:

- `tanstack-start:start-manifest-capture-client-build` (the one with the multiple-entries error)
- `tanstack-start-core:dev-server` / `:preview-server` / `:dev-server:injected-head-scripts` (SSR middleware Storybook doesn't need)
- `tanstack-start-core:post-build` (irrelevant to Storybook's static output)
- `tanstack-start-core:virtual-client-entry` (Storybook ships its own iframe entry)

The config / start-compiler / import-protection / router-plugin sub-plugins **survive the filter** because (a) they don't conflict with Storybook and (b) downstream plugins error with `Cannot get config before root is resolved` if the config plugin is removed.

Verification: `npm run build-storybook` succeeds in **18.48s** (W123 SW1 baseline 8.15s; +10s due to remaining tanstackStart plugins running on Storybook's iframe build, an acceptable tradeoff to keep visual regression infra working).

## Honesty probe — what's NOT verified in this wave

1. **Full LHCI 9-URL × 3-run sweep NOT completed.** First attempt (SW2 verification) hit `runtimeError: NO_FCP` on `/` because the existing dist/ was built without `VITE_LHCI=true` (auth bypass tree-shaken out) — `useProfileSync` then attempted real `/api/v1/users/me` requests against a backend that wasn't running, the auth provider failed, and React never rendered any content. After rebuilding with `VITE_LHCI=true npm run build`, a 1-run focused LHCI sweep on `/` was launched in the background of this commit but had not completed at commit time (each run is taking ~10 min vs W124's ~2 min — the SSR-rendered shell adds overhead). **Phase 1 design doc requirement** ("LHCI baseline preserved") is partially verified — the build infrastructure produces a shell with all the right meta tags + theme detection + script tags + modulepreload, and a `vite preview` GET / returns 200 with 9,428 bytes of valid HTML, so the shell IS reachable; but the actual Lighthouse Perf / CLS / A11y / LCP numbers are not captured in this commit. **Wave 126 work**: dedicated 9-URL × 3-run baseline sweep with VITE_LHCI build to compare against W124 SW6 numbers (/ 0.54/CLS 0.017, /dashboard 0.46/CLS 0.017, /events 0.47/CLS 0.062, etc.).

2. **E2E test suite NOT run.** `npx playwright test --project=chromium tests/e2e/a11y-public.spec.ts` timed out at 180s waiting for `webServer.command` (`npm run build && npm run preview`). The Phase 2 build is slower than pre-W125 (~30+s vs ~7s) due to TanStack Start runtime additions and SSR pipeline, exceeding Playwright's default webServer timeout. **Wave 126 work**: bump `playwright.config.ts` `webServer.timeout` to 300s (or 600s for safety), then verify `a11y-public.spec.ts` 4/4 chromium + `url-state-persistence.spec.ts` 6/6 chromium baselines.

3. **`npm run dev` not smoke-tested in Phase 2 final state.** Phase 1 SW1 verified `vite dev` works (with the filter + appType="spa" workaround); Phase 2 removed those workarounds in favor of the shellComponent / ssr: false combination. Logical equivalent should hold — tanstackStart's dev-server-plugin uses the same SSR pipeline as preview-server-plugin, which we know works. But not directly re-verified in this commit cycle.

4. **`build x 3` reproducibility NOT explicitly re-verified post-Phase-2.** Phase 1 SW1 confirmed the build was reproducible (hash `index-CjlHMWh3.js` 116,099 bytes × 3 runs). Phase 2 introduces new infrastructure (shellComponent, ssr: false, stub context, post-build script) — sole observed bundle hash post-Phase-2 is `index-B7yKlNd5.js` 137,813 bytes (verified once across two consecutive runs in early SW2 testing; full × 3 reproducibility check not in this commit cycle). **Wave 126 work**: verify reproducibility, document the +21 KB main chunk delta vs SW1.

5. **Post-build script reliability cross-platform untested**. The script works on the dev workstation (Windows) but the run-build.mjs spawn-child mechanism relies on node's child_process behavior that has been finicky elsewhere (see commit message). Linux CI and macOS dev workstations may interact differently — especially the `npm run build && npm run build:shell` chain pattern that was abandoned for the spawn-child approach.

6. **No CHANGE recorded to LHCI gate thresholds.** W120 SW2 ratchet (CLS error@0.10, Perf error@0.40 — relaxed to warn@0.40 in routine-e5 close-out 2026-05-04 due to dev/CI calibration drift) is preserved unchanged. Phase 2 should hoist Perf above 0.50 in both dev + CI, justifying re-ratcheting Perf back to error@0.40 (or higher), but that decision waits for the W126 LHCI baseline sweep that's deferred from this wave.

7. **No measurement of bundle-size impact on real-user perf.** Main chunk +21 KB (CjlHMWh3 116,099 → B7yKlNd5 137,813) due to TanStack Start runtime additions for shell handling. Total client JS (sum of all `dist/client/assets/*.js`) is comparable to W124 because the bundle is split into many smaller chunks instead of fewer larger ones. LHCI sweep would quantify whether the extra bundle bytes affect TBT / LCP positively (better caching granularity) or negatively (more HTTP round-trips on cold cache).

8. **`build:shell` lifecycle hook documented as deferred fallback.** package.json has `"build:shell": "node ./scripts/post-build-shell.mjs"` so users who hit the spawn-child issue on edge cases can run `npm run build && npm run build:shell` manually. CI doesn't use this; CI uses `npm run build` which spawns the post-build script transparently.

## Phase 2 prep notes (for W126+)

Per design doc §3 Phase 3-6:

- **Phase 3 (W126, ~6-10 h)**: auth-at-edge — cookie-based session handling so `_auth.tsx` beforeLoad guards see real auth on SSR. Recommended path 3a (lightweight: keep AuthContext + decode JWT in server entry, cookie reads). Removes the `SSR_STUB_AUTH` stubs from `router.ts`.
- **Phase 4 (W127, ~4-6 h)**: Caddy SSR forwarding rules — production deployment serves SSR-rendered HTML through Caddy reverse-proxy + Nitro server runtime (Node target). Health checks, rolling deploys, k8s sizing.
- **Phase 5 (W127, ~3-5 h)**: browser-API safety guards — audit `frontend/src/` for `window` / `localStorage` / `IntersectionObserver` / `ResizeObserver` / canvas usage in code that runs server-side. Mark routes with heavy browser deps as `ssr: 'data-only'` (e.g. `/map` for maplibre-gl, `/activity` for html-to-image / jspdf already lazy-loaded).
- **Phase 6 (W128, ~6-8 h)**: testing matrix + canary rollout — full Playwright suite on SSR build, Chromatic visual regression baseline on SSR-built stories, manual smoke via chrome-devtools-mcp on all 9 URLs. Caddy traffic split 10% → 25% → 50% → 100% over 1-2 weeks.

After Phase 6, the LHCI baseline can be re-measured and gates ratcheted (Perf error@0.40 → error@0.60+, LCP error@2500ms, etc.) — currently locked at "W124 baseline preserved" pending the SSR rollout.
