## 1. Цель и граница

**v1.0.0** — это принятый по ТЗ продукт. Нужно:
- живые сценарии, проверенные дважды подряд;
- утверждённый визуал;
- отсутствие открытых P0/P1 по безопасности;
- зелёные обязательные проверки и обычный merge в `main`;
- шесть образов от существующего main-only producer;
- релиз `v1.0.0` с перечнем ограничений.

**Вне MVP (v1.1):**
- мутационные линии и mutation score;
- coverage ratchet (Q3);
- три сопоставимых полных CI-прогона;
- kind-развёртывание приложения и Envoy Gateway;
- RPO/RTO и полная наблюдаемость;
- deployed BE-02/MIG-PASS;
- WS-нагрузка;
- лабораторный протокол производительности;
- массовая чистка кода. Подробности — в разделе 12.

## 2. Решения, которые план не пересматривает

- ГУУ остаётся брендом внутреннего демо. Данные и аккаунты синтетические, роли — student, teacher и admin.
  Публичное использование названия и логотипа и данные реальных пользователей решаются отдельно (§12).
- Работа ведётся на `egorribun`, каждый PR идёт `egorribun` → `main`, допускается только обычный merge.
  Действуют 78 обязательных пар context/integration и CodeQL `code_scanning`. Любое изменение ruleset
  или обязательных проверок требует решения владельца по ADR-047.
- Покрытие Tier 0 и все миграции держатся на 100% по каждой применимой метрике. Прочие текущие floors
  из `quality/quality-contract.json` остаются до Q3. Пороги не снижать.
- Мутационные линии исключены из MVP (решение владельца 2026-11-13). Их красный nightly не блокирует
  приёмку.
- Целевое окружение MVP — Docker Compose (2026-11-09). kind + Calico служит средой доказательств только
  для AUD-169, AUD-188, AUD-189, AUD-251 и AUD-438 (2026-11-12). Развёртывание приложения в kind и
  Envoy Gateway относятся к v1.1.
- Продуктовая приёмка идёт на Core-стенде. Full stack проходит отдельный smoke на замороженном
  кандидате из `quality/frozen-rc.json`.
- В MVP не добавлять:
  - обязательную MFA;
  - учебные цели и посещаемость;
  - CDC;
  - сущности помещений и вместимости;
  - QR-приход и лимиты мест;
  - backend GraphQL.

  Новая учебная модель оформляется отдельным ADR после MVP.
- Оси приёмки: RU/EN и светлая/тёмная темы, обязательные ширины 390, 768 и 1440 px. На 360 и 1024 px
  проверяются только меню, таблицы и найденные адаптивные дефекты. Физические устройства, внешние
  SMTP/push-провайдеры и field CWV остаются ручными проверками (§5.4).
- Язык документов: ТЗ, план и STATUS пишутся по-русски, ADR, runbooks и код — по-английски.

## 4. Критический путь

1. **AUD-154.**
   - Нужен второй подряд зелёный полный Core на `main`, не чаще одного запуска в 2 часа.
   - Затем один коммит переводит шесть файлов счёта аудита на 512/512, по hosted-evidence.
2. **Открытые PR.** Слить их обычным merge после всех обязательных проверок и закрыть перенесённые
   черновики облачного агента.
3. **Один локальный Core-стенд на замороженном SHA `main`**, на нём этапы 4 и 5:
   1. скриншоты пакетов этапа 4 (§6.1);
   2. backup/restore этапа 5 (§7.3);
   3. остановка стенда (teardown).
4. **Этап 3: строки матрицы** — пакетами по 5–6 строк, каждый пакет в своём PR, с hosted PR Core
   (§5.2).
5. **Этап 4: остаток после утверждения пакетов** — Linux-эталоны, Lighthouse, циклы stories, a11y
   (§6.2–6.3).
6. **Этап 5: review.** Независимый review auth, сессий и данных и решения владельца из §9.
7. **Freeze и выпуск (§8):**
   1. выбрать RC;
   2. full smoke;
   3. main-push проверки;
   4. образы;
   5. тег и release notes.

Пункты 3–6 можно готовить параллельно, а итоговая приёмка требует зелёного Core на финальном source.
Тяжёлый локальный процесс запускается только один. Перед build, full E2E и Lighthouse загрузка RAM
должна быть не выше 75% и свободно не меньше 8 GiB. Во время работы действует guard: 85% или 4 GiB.

- **Core.**

## 6. Этап 4: визуал и производительность

### 6.1 Пакеты экранов

- **Пакет 1** (решение владельца 2026-11-23):
  - экраны: вход, регистрация и главная; новости и мероприятия; расписание и карта; мессенджер,
    профиль и настройки;
  - оси: RU/EN, светлая и тёмная темы, 1440 и 390 px.
- **Доставка.** Пакет передаётся локальным HTML-файлом с сеткой скриншотов, без публикации: на экранах
  виден бренд ГУУ. Владелец отвечает в чате.
- **Инструмент** — `frontend/scripts/authenticated-visual-audit.mjs`, против живого стенда.
  - Переменные: `VISUAL_CAPTURE_MATRIX=1`, `SOURCE_SHA`, `TEST_EMAIL`, `TEST_PASSWORD`, `ORIGIN`,
    `OUT_DIR` (вне checkout) и `VISUAL_WIDTHS`.
  - Его allowlist `ROUTES` не знает вход, регистрацию и детальные страницы новостей и мероприятий.
    Расширить allowlist с тестами; новый инструмент не создавать.
- **Утверждение** фиксируется так же, как у Home12: `frontend/visual-baselines/live/<package>/`,
  `approval.json`, PNG и SHA-256, sourceCommit и браузер.

### 6.2 Эталоны и бюджеты

- **Linux-эталоны** снимаются после утверждения пакета в официальном контейнере Playwright той же
  версии, что зависимость проекта: `mcr.microsoft.com/playwright:v1.65.1-noble`, закреплённый по
  digest. Linux-эталон канонический. Сейчас в репозитории есть только 5 эталонов win32.
- **Бюджеты** по действующему измерителю `frontend/scripts/check-bundle-budget.mjs`:
  - main JS — меньше 500 KB;
  - initial JS gzip — не больше 420 KiB;
  - общий lazy JS — не больше 280 KiB;
  - чанк MapLibre 6.18.0 — не больше 290 KiB, только с доказательствами по
    [ADR-049](../../adr/ADR-049-maplibre-lazy-chunk-budget.md).

### 6.3 Lighthouse, память, доступность

- **Lighthouse.** Один проход по подготовленным маршрутам: вход, главная, новости и мероприятия, профиль
  и настройки, мессенджер. Сохранить конфигурацию, маршруты, отчёт и SHA через существующий collector.
  Действующие LHCI assertions не отключать.
- **Stories.** 20 последовательных циклов открытия и закрытия, память выходит на plateau (R45).
- **Доступность.** Нет serious и critical находок axe на принятых экранах, reduced motion проверен.
- **Мимо MVP (v1.1):** CLS навбара < 0,1, long tasks карты ≥ 50 ms, INP ≤ 200 ms, Lighthouse ≥ 0,95.
  Готовые измерители сохранить.

## 7. Этап 5: безопасность, ledger, данные

### 7.1 Безопасность

- Нет открытых P0 и P1. AUDIT-2026-10 доводится до 512/512 (§4, п. 1).
- Реестр из 63 ID платформенного аудита (раздел «Findings ledger» в
  [audits/INDEX.md](../../audits/INDEX.md)) перепроверяется на SHA кандидата. Каждый ID получает статус
  «закрыто с evidence», «отклонено с обоснованием» или «перенесено в v1.1 с владельцем».
- Нужен независимый review auth, сессий и данных; кто и когда его проводит, решает владелец (§9). Порядок
  отзыва по [ADR-006](../../adr/ADR-006-websocket-auth-tickets.md) подтверждается в том же review.
- Остаточный риск токена сброса пароля в JetStream записывается как принятый владельцем либо
  исправляется (§9).

### 7.2 Compose и хранилище

- **Чистый старт:** проверить health и readiness, корректную остановку, повторный запуск, замер RAM и
  CPU. Пользовательские тома и `.env` не трогать.
- **S3:**
  - реальные Put, Head, Get и Delete;
  - presigned URL;
  - приватный доступ;
  - целостность объекта.

### 7.3 Разовый backup/restore

Restore проводится один раз, на том же локальном стенде, что и скриншоты (решение владельца 2026-11-23).
Процедура и ограничения — в [runbook](../../runbooks/database-backup-restore.md).

1. Перевести стенд в режим `quiesce`. Работать остаются только PostgreSQL и MinIO.
2. Запустить `scripts/backup_db.py snapshot --confirm-source-quiesced` в отдельный backup-бакет.
3. Выполнить `restore-snapshot` в новую базу `restore_*` и новый бакет с пустым префиксом. Целевой
   public base должен быть абсолютным URL: так требует `attachments.url`.
4. Проверить результат:
   - Alembic revision и число строк по таблицам совпадают с источником;
   - ссылки в восстановленной БД указывают на целевой base;
   - объект, прочитанный через `S3Storage` по ссылке из восстановленной БД, совпадает с исходным по
     SHA-256;
   - исходная БД и бакет `uploads` не изменились.
5. Записать в STATUS логи и контрольные суммы, без секретов.

RPO и RTO этим не сертифицируются (v1.1).

## 8. Этап 6: выпуск

Механика уже есть в репозитории, её не переписывать.

### 8.1 Кандидат

- Тег и публикация допускаются только с согласия владельца. Кандидат — SHA `main` после последнего
  продуктового merge. После freeze любое изменение поведения создаёт новый кандидат, и затронутую
  приёмку повторяют.
- **Порядок активации.** Кандидат фиксируется через `quality/frozen-rc.json` (`source_sha`).
  Валидатор — `scripts/quality/resolve_frozen_rc_manifest.py`, спецификация —
  [frozen-rc manifest](../specs/2026-10-19-frozen-rc-manifest.md).
  - Коммит манифеста сам сдвигает HEAD `main`, а `build-release-images.yml` и `release.yml` требуют
    SHA релиза = текущему `main`.
  - Предлагаемый порядок (решение владельца, §9):
    1. кандидат X — `main` после последнего продуктового merge;
    2. PR только с манифестом X сливается, и `main` становится Y;
    3. full smoke проверяет X;
    4. релиз выпускается с Y.

    `git diff --name-only X Y` при этом должен совпадать с `quality/frozen-rc.json`.

### 8.2 Последовательность

1. **Full smoke.** `gh workflow run live-acceptance.yml --ref main`: job `frozen-rc-full-smoke`
   поднимает `--stack full` на X, прогоняет `e2e --mode full` и делает stop. Receipt имеет вид
   `frozen-rc-live-receipt-<sha>-<run>-<attempt>`.
2. **Main-push проверки.** Push-прогон `ci.yml` на Y проходит целиком.
   `scripts/quality/collect_release_check_evidence.py` сверяет его с
   `quality/release-required-checks.json`.
3. **Образы** — только с согласия владельца на публикацию в GHCR.
   - Запуск: `gh workflow run build-release-images.yml -f release-sha=Y -f quality-run-id=<run>`.
   - Producer собирает ровно шесть образов: backend, frontend, ws-hub, gateway, file-processor и caddy.
     Он выполняет Trivy, SBOM, подпись cosign и attestation и публикует тег `<release-sha>`.
4. **Релиз** — только с согласия владельца.
   - Запуск: `gh workflow run release.yml` с release-sha, quality-run-id, image-build-run-id и
     image-build-run-attempt.
   - semantic-release на `main` создаёт тег и GitHub release с `release-image-manifest.json`.
   - Тегов в репозитории пока нет, поэтому первый релиз — `v1.0.0`. Проверить это перед запуском.
5. **Release notes:**
   - состав;
   - ограничения (раздел 10);
   - release SHA;
   - manifest образов и evidence.

   Source после сертификации ради вписывания run ID не меняется.
