# ADR-053: Operator-scoped single-organization MVP authentication

## Status

Scope accepted by the owner on 2026-11-02 and implemented in source. The full
source-bound hosted acceptance below remains pending; this document is not
evidence of a deployed or verified fix.

## Context

The application runtime uses `ue_app`, without superuser, BYPASSRLS, or membership
in `ue_rls_bypass`. The baseline protects `users` with forced tenant RLS. Existing
login searched that table before it had a trusted tenant, while the token issuer
deliberately omitted tenant identity. Consequently ordinary unauthenticated
credentials could not bootstrap an application session on that role.

The baseline already contains `users.tenant_id` referencing `tenants.id`. This
decision uses that existing column; it does not introduce a migration, database
function, policy exception, lookup role, or privileged connection.

## Decision

- An operator explicitly configures `MVP_TENANT_ID` as a UUID identifying the
  deployment's one organization. It is not generated by request handling and is
  never inferred from a Host, email suffix, raw tenant header, group selection,
  or invitation. There is no built-in organization identifier.
- Absent configuration does not enable this mode. Existing fail-closed tenant
  RLS remains; it is not a supported working MVP authentication deployment.
- Configuration supplies routing scope only. It does not authenticate a user,
  session or role, and does not bypass endpoint authorization, MFA, rate limits,
  revocation, or PostgreSQL RLS.
- Request database sessions require the configured tenant to exist and be
  active. Missing, inactive, mismatched or bypass-scoped requests fail closed.
  The application does not create, reactivate or adopt tenants on HTTP requests.
- Genuinely anonymous requests may use the operator's routing scope. Present
  invalid identity assertions are rejected, not downgraded to anonymous access.
  A verified gateway assertion or JWT must name the configured tenant. A raw
  unsigned tenant hint cannot switch the deployment's scope.
- Registration explicitly assigns the configured tenant. Existing group and
  invitation checks remain in the ordinary application transaction; they do not
  establish an alternative tenant. Public multi-organization registration is
  deferred to a separate reviewed design.
- After credential/MFA verification, session issuance locks the stored user
  row and derives `tenant_id` from that row. Null or foreign membership is
  rejected. Caller-provided claim overrides are not authoritative. Subsequent
  gateway and direct-backend authentication check the claim and stored user.
- Old tokens without tenant identity require reauthentication in this mode.
  Rejected access-token cookies are cleared so the browser can retry login.
- Transaction-local GUCs and task context restoration remain in force. No
  session-wide tenant setting or transferable bypass flag is introduced.

## Operations and bootstrap

Provision the intended active tenant through an authorized operator process,
then configure the matching UUID before authentication acceptance. Never reuse
worker or migration credentials for API authentication. Owned synthetic stands
use their independently verified project identity for both seed assignment and
the explicit configuration, rejecting collisions or inactive existing rows.

The existing `/health/ready` probes database connectivity through the engine;
it does not acquire an application request session and is not a claim that the
tenant was provisioned or login accepted. This preserves the owned stand's
ready-then-seed ordering. Product acceptance must exercise seeded authentication
after readiness. A general deployment must not mistake connectivity readiness
for successful tenant/authentication provisioning.

## Required evidence

Run on an acknowledged disposable PostgreSQL baseline with a genuine ordinary
application login: registration, existing-account login, same generic rejection
for unknown/incorrect credentials, MFA and reset continuation, signed token and
subsequent authenticated request. Check inactive/null/foreign membership,
tampered and absent identity, foreign rows, anonymous protected-endpoint denial,
and pooled-connection/context cleanup. Verify that baseline schema parity and
role restrictions are unchanged. Mock/unit and static checks do not replace
this hosted source-bound acceptance.
