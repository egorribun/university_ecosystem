## Context

The SSR auth-at-edge layer through Node SSR was NOT closeable post-polish-v2 because `frontend/src/ssrAuth.ts` uses `jose.createRemoteJWKSet` (RS256 default) but dev backend signs HS256 → signature check fails → SSR `beforeLoad` redirects to /login.

### Why Path (a) Backend RS256 over Path (b) HS256 fallback

Path (a) matches production deploy assumption per W125+ SSR design intent: jose's `createRemoteJWKSet` is the canonical pattern + backend's existing `/.well-known/jwks.json` endpoint at `app/api/well_known.py` already publishes RS256 public keys + gateway's existing `StartJWKSRefresher` (MOD-W17-03) polls JWKS endpoint with atomic key swap. Path (b) would bake dev-only SECRET_KEY plumbing into production frontend SSR runtime — divergent dev/prod paths. Path (a) is the right architectural choice even if upfront cost is slightly higher.

## Critical findings from 3 Explore agents (pre-implementation)

### Finding 1 — Backend RS256 is code-ready but Docker startup hardcodes HS256

**Source**: Explore agent #1 mapping of:
- `app/core/config/mixins/jwt_settings.py` (293 lines)
- `app/api/well_known.py` (93 lines)
- `app/services/auth/session_service.py` lines 150-250
- `start-docker.ps1` lines 126-148

**Key facts**:
- `jwt_settings.py:25` defaults to `algorithm: str = "RS256"` (production assumption already enforced via env validator at lines 87-139)
- Registry auto-loads `.secrets/jwt_rs256.pem` if RS256 + path exists (lines 199-230); falls back to HMAC with warning if missing in dev
- JWKS endpoint at `/.well-known/jwks.json` already extracts public key from PEM, returns RFC-7517 JWK; tested by `tests/test_jwks_endpoint.py`
- `start-docker.ps1:126-148` writes `ALGORITHM=HS256` (hardcoded) and **never generates `.secrets/jwt_rs256.pem`** — this is the actual gap

**Implication**: Backend code = ZERO changes. SW1 needs only RSA key gen in `start-docker.ps1` + flip `ALGORITHM=HS256 → RS256` in `.env.docker` + add `JWKS_ENDPOINT` to gateway env. ~2-3h realistic (refines W137 prompt's anticipation that "expect Explore-agent discovery may reveal that backend RS256 enablement requires more steps").

### Finding 2 — `VITE_BACKEND_ORIGIN` is BAKED at frontend build time (CRITICAL TRAP)

**Source**: Explore agent #2 mapping of:
- `frontend/vite.config.mts` lines 208-214
- `frontend.Dockerfile` lines 25-26
- `frontend/scripts/server-prod.mjs` (full read)
- `frontend/src/ssrAuth.ts:79`

**Key facts**:
- `ssrAuth.ts:79` reads `import.meta.env.VITE_BACKEND_ORIGIN` (build-time literal substitution by Rolldown DCE, NOT runtime env lookup)
- `frontend.Dockerfile` `ARG VITE_BACKEND_ORIGIN=""` + `ENV VITE_BACKEND_ORIGIN=$VITE_BACKEND_ORIGIN` — empty string passed during build
- `docker-compose.full.yml` `frontend.build.args.VITE_BACKEND_ORIGIN: ""` (empty) per Explore agent observation
- Result: ssrAuth.ts:79 falls back to `http://localhost:8000` (hardcoded default) → unreachable from inside frontend container → JWKS fetch fails silently → SSR returns UNAUTH → redirect

**Implication**: Even if backend successfully switches to RS256 (SW1), the SSR layer still cannot fetch JWKS without a Docker build arg fix. SW3 is on the critical path. ~30 min.

### Finding 3 — gRPC health probe binary not vendored; tempo/loki need sidecar

**Source**: Explore agent #3 mapping of:
- `services/file-processor/Dockerfile`
- `services/file-processor/cmd/file-processor/main.go` lines 277-280
- `docker-compose.full.yml` tempo + loki blocks (lines 552, 572)
- `infrastructure/observability/tempo.yaml` line 7 + loki.yaml line 8

**Key facts**:
- file-processor: gRPC health handler ALREADY REGISTERED at startup (`main.go:277-280`). Need binary in Dockerfile + compose healthcheck. Pattern: spicedb already does this (`docker-compose.full.yml:435`).
- tempo (`grafana/tempo:2.10.3`) + loki (`grafana/loki:3.7.1`): both expose HTTP `/ready` endpoints on `:3200` / `:3100` per their YAML configs. Distroless images lack any HTTP client.
- Sidecar pattern with `curlimages/curl:latest` + `network_mode: service:tempo` (or `service:loki`) is the cleanest workaround.

**Honest §Honesty caveat**: sidecar healthcheck does NOT mark the tempo/loki container itself as "healthy" — only the sidecar. `docker compose ps` shows sidecar healthy, target container "running" without explicit "healthy" marker. By-design limitation; not a fix without custom Dockerfile builds.

### Finding 4 — Gateway already has JWKS hot-reload infrastructure

**Source**: grep on `services/gateway/middleware/auth.go`.

- `MOD-W17-03` already implemented: `StartJWKSRefresher(ctx, endpoint, interval, logger)` polls JWKS endpoint + atomic key swap
- Gateway env var `JWKS_ENDPOINT` (default empty = disabled)
- No code changes needed; just set `JWKS_ENDPOINT=http://backend:8000/.well-known/jwks.json` in compose gateway env
