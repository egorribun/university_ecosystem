### Agent 2 (Path a-auth (z) #10 diagnosis): CRITICAL JWX LIBRARY DISCOVERY

**Token shape audit** (from [.secrets/temporal_api_key](../../.secrets/temporal_api_key) read at runtime):
- Header: `{"alg":"RS256","kid":"primary","typ":"JWT"}` ✓ matches backend JWKS kid
- Payload: `{"sub":"file-processor-service","aud":"temporal","iat":...,"exp":...,"jti":...}` ✓ standard claims
- Signing algorithm: PowerShell .NET 8 `RSASignaturePadding::Pkcs1` (RS256-PKCS1-v1_5 per RFC 7518 §3.1) ✓
- Hash: SHA256 ✓
- Key size: RSA-2048 ✓
- JWKS at [app/api/well_known.py:54-67](../../app/api/well_known.py) exports `kid="primary"` + `alg="RS256"` + base64url `n`+`e` from `RSAPublicKey.public_numbers()`

**CRITICAL DISCOVERY** (NEW W143 Phase 1, not in W142 audit):
- Temporal Server v1.30.2 uses **`lestrrat-go/jwx` library** for JWT verification (NOT direct Go `crypto/rsa`)
- The error message "crypto/rsa: verification error" originates from `interceptor.go:145` in Temporal Server source but is JWX's wrapped error wording, masking the actual JWX-internal verification failure
- Implication: W142's diagnosis ("crypto/rsa: verification error" face value) was incomplete; the actual library/code path needs separate investigation

**3 root cause hypotheses** (per Agent 2 analysis):

1. **Scenario A — JWKS payload structural byte-encoding mismatch** (MOST PROBABLE):
   - Python `cryptography` library at well_known.py:54-67 derives `n` and `e` via `numbers.n.to_bytes(..., byteorder="big")`
   - PowerShell .NET 8 `RSA.ExportSubjectPublicKeyInfoPem()` may produce slightly different byte ordering or padding when re-imported on Temporal's side
   - JWX may require **exact byte-identical representation** between token-signing pub key and JWKS-published pub key
   - Mitigation hypothesis: standardize byte encoding (zero-pad to RSA key length, big-endian)

2. **Scenario B — JWKS cache/fetch race condition**:
   - JWX v2 default: lazy fetch on first Verify() call (15min cache TTL)
   - If backend restarts between file-processor token mint and Temporal first-verify, JWKS `kid="primary"` may have rotated keys
   - Token signature was generated with OLD key, Temporal tries to verify against NEW key → verification error
   - Mitigation hypothesis: ensure JWKS endpoint stability + force JWX cache refresh

3. **Scenario C — RSA-PSS padding heuristic**:
   - RFC 7518 mandates RSA-PKCS1-v1_5 for RS256
   - Some JWX implementations (older versions or forks) try RSA-PSS detection heuristics first; fail incorrectly
   - PowerShell uses Pkcs1 (correct) but JWX might detect PSS first
   - Mitigation hypothesis: explicit `alg: "RS256"` enforcement check via direct JWX verify in test
