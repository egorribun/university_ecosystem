## Tier 1 — JWT (d) Hybrid: backend embeds claim + leverages existing gateway revocation

### Problem

W135 SW2 discovered that `services/gateway/middleware/auth.go:720` reads `claims.IsActive` from the JWT payload, but backend's `SessionService._mint_jwt` (`app/services/auth/session_service.py:194-218`) does NOT embed `is_active` in JWT payload (only `sub/aud/iat/nbf/exp/jti`). Result: 100% of authed gateway requests return 403 "user account is not active". Direct backend on port 8000 returns 200 with `is_active: true` correctly.

The gateway+backend protocol drift existed undetected for 130+ waves because no automated test exercises the gateway's claim check end-to-end.

### Decision: JWT (d) Hybrid via existing Redis pub/sub

User chose option (d) — JWT carries `is_active` claim AND gateway maintains a revocation set for immediate deactivation effect. Three other options were considered:

- **(a) Embed in JWT only** — fast but stale; deactivated user keeps access until JWT expires (~15-60 min)
- **(b) Gateway DB lookup with cache** — correct + fast steady-state; +DB query per cache miss
- **(c) Remove gateway check** — simplest; defense-in-depth lost

**Critical exploration finding**: gateway already has the revocation infrastructure for option (d). The pre-existing `ListenForRevocations()` (`auth.go:362-416`) consumes Redis pub/sub channel `session:revocations`, adds JTIs to `revoked:jti:{jti}` keys with L1 cache + XFetch probabilistic refresh. Backend just needs to publish JTIs on user deactivation — no new NATS subject required.

### Architecture

### Defense-in-depth properties

- **Fast path**: JWT claim check on every authed request (~ns)
- **Correctness**: Revocation set check after claim (~µs L1 cached, ~ms Redis fallback)
- **Stale JWT scenario**: Deactivated user with valid JWT in hand gets caught at revocation set within seconds of deactivation publish
- **Backwards-compat note**: Pre-W136 JWTs in the wild won't have `is_active` claim. Go json unmarshal defaults missing `bool` to `false` → gateway returns 403 → user re-logs in. Acceptable under no-deploy scope (no production traffic).

### chrome-devtools-mcp Windows wall: Playwright (b) alternative

The W135 SW2 visual-smoke attempt hit `Accessibility.getFullAXTree timed out` + `Runtime.evaluate timed out` on Windows + headless Chrome (same family as W132 polish round 2 perf APIs). `list_network_requests` + `list_console_messages` worked fine — the wall is on snapshot/eval surface specifically.

W136 SW3 adds Playwright-based visual smoke script using **real Chrome** (`channel: 'chrome'`) with extended timeouts. Bypasses chrome-devtools-mcp's headless wall entirely. Mirrors the chrome-devtools-mcp output patterns (console messages, network requests, screenshot) for drop-in substitution in future visual-smoke documentation.

The W135 SW2 NotNullViolation must be from a different column OR the INSERT site has wrong assumption. ## Tier 2 — build-orchestrated.mjs structural fix + Workbox export + Linux CI

### Problem

W135 SW3 retired `wave127-build-x3.sh` Windows watch+kill workaround via integrated `frontend/scripts/build-orchestrated.mjs`. Empirical findings showed two hang causes (not just vite-plugin-pwa as W126 polish #3 assumed):

1. **vite-plugin-pwa Windows hang** — closed at orchestration level via `BUILD_SKIP_PWA=true` env-flag + standalone `workbox-build.injectManifest`
2. **Second hang in tanstackStart-core plugin chain** — kill-after-artifacts SIGTERM pattern works as fallback but is NOT a structural fix

W136 SW5 instruments `build-orchestrated.mjs` with `process._getActiveHandles()` + `process._getActiveRequests()` at hang detection point to identify which plugin holds the event loop, then either fix locally OR file upstream issue with full repro.

### Decision: Q3a (Medium) trace approach

User chose the Medium investigation depth (`process._getActiveHandles()` trace) over Light (file upstream + cleanup hook only) and Heavy (replace with nitro plugin — anti-recommended under no-deploy scope, would cascade-break PWA + LHCI).

Common Node.js handle types to identify:
- `Timer` — forgotten setInterval/setTimeout (likely candidate for `tanstack-start-core:post-build`)
- `FSWatcher` — watcher not closed (possible for vite-plugin-pwa OR file-watcher plugin even when disabled)
- `ChildProcess` — subprocess not exited (possible for swc/oxc/esbuild workers)
- `TLSWRAP`/`TCP` — socket left open (unlikely in build context)

Outcome decision tree:
- **Path (b) — local fix**: add explicit cleanup hook in build-orchestrated.mjs subprocess (e.g. `process.on('exit', cleanup)` OR `subprocess.unref()`). Closes hang structurally; kill-after-artifacts becomes last-resort SIGKILL fallback.
- **Path (a) — upstream issue**: file at vitejs/vite OR ryanflorence/tanstackStart with full repro. Document in commit body + AUDIT.

### Workbox config drift fix

W135 SW3 hardcoded the Workbox config in `build-orchestrated.mjs:60-68`, mirroring `vite.config.mts:357-382`. Drift risk: vite.config.mts changes don't propagate to Windows local builds.

Fix: extract `PWA_INJECT_CONFIG` named export from `vite.config.mts`; import via `vite.loadConfig()` API (supports TS natively, no new dependency).

### Linux CI validation

NEW `.github/workflows/build-orchestrated-linux.yml` workflow_dispatch trigger validates that build-orchestrated.mjs produces BYTE-IDENTICAL output on Linux runner (where the Windows hang doesn't occur). Asserts hash matches Windows local baseline.
