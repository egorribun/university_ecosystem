## §3. Recommended approach

Sequential SW commits closing structural debt in dependency order. Each SW
produces a verifiable artifact; later SWs depend on earlier ones reaching
`(healthy)` state.

### Critical sequencing decision (per Q2 = "backend creates streams")

- **SW1** (backend `files.process` stream creation) MUST land before SW3
  verification, because SW3's `depends_on: backend service_healthy`
  guarantees the stream exists before file-processor subscribes
- **SW2** (schema.graphql Dockerfile COPY) is independent — can land in any
  order; combined SW1+SW2+SW3 effect brings file-processor to `(healthy)`
  for first time post-W137 SW5
- **SW4** (env-flag-guards) depends on SW1+SW3 reaching stable state
  (visual-audit.yml CI verifies the full chain)
- **SW5** (Path (a-auth)) is independent of SW4 but HIGH RISK; recommend
  after SW4 stabilizes so iter-blocked surface isn't compounded
- **SW6** (Tier 3 selection) depends on SW4 outcome
- **SW7** is final (after all others)

### Why "backend env-flag-guards" path for SW4 (not "add SpiceDB+ES services")

Pragmatic for read-only SSR audit routes that don't exercise auth/RBAC
layer. Adds `BACKEND_SKIP_SPICEDB` + `BACKEND_SKIP_ELASTICSEARCH` env flags
+ extends existing `environment == "testing"` NATS gate. Closes W138 #4 +
W139 #8 in one shot. Backup plan if env-flag-guard scope creeps: pivot to
"add SpiceDB+ES services to GitHub Actions services block" path — slower
CI but structurally simpler.

### Why "backend creates streams + file-processor waits" for Q2

Matches production architecture (single source of truth). Backend's
`NatsTaskBroker.connect()` already has the pattern (TASK_QUEUE creation);
adding `files.process` is a single edit. Combined with `depends_on:
backend service_healthy`, file-processor reliably subscribes to existing
stream.
