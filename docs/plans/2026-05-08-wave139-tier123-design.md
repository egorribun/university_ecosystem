## §3. (z) Path discovery — Path (a) auth NOT feasible with current Temporal image

### 3a. Finding

User's Q2 chose "Path (a) structural rebind + token auth (~2-3h)". Reality (per Context7 verification):

- **Path (a-rebind only)**: Drop `--ip 127.0.0.1` → Temporal listens on all interfaces of its container. file-processor reaches it via service-name DNS `temporal:7233`. **Implementation: ~30-60 min**. **Security**: relies on Docker `internal` network isolation (same posture as Postgres/Redis in this compose file — both unauth'd within isolated network). Acceptable for dev compose.

- **Path (a-rebind + auth)**: Requires switching from `temporalio/admin-tools:1.30.2` image to `temporalio/server` image + custom `auth_config.yaml` + dynamicconfig + claim mapper config. Additionally requires JWKS endpoint integration (file-processor signs JWT, Temporal Server validates via `/.well-known/jwks.json`). **Implementation: ~3-5h**, plus may surface (z) sub-paths during integration. Could push wave beyond Q3 +3h+ expansion budget envelope.

### 3b. Recommended pivot

**Pursue Path (a-rebind only) in W139** (~30-60 min, SW2). Defer Path (a-auth) to a focused W140+ wave with proper scoping (Temporal config file authoring + image change + integration verification = full focused scope, not a side effect of W139's broad Tier 1+2+3 scope).

### 3c. Honest framing for §Honesty

This pivot **partially closes** W137 §Honesty #5. The closure framing changes from:
- Pre-W139: "file-processor temporal-localhost dev limit (P0-03 trade-off; needs structural fix)"

To:
- Post-W139: "file-processor reaches Temporal in dev compose via service-name DNS (rebind W139 SW2). Token-based auth on Temporal Server deferred to W140+ as separable focused scope (requires image switch + custom config — not feasible with current `admin-tools` dev-server image which has no auth flags per Context7 `/temporalio/documentation` validation)."

This is more honest than "fully closed" because the auth refinement IS deferred. But the **dev-compose-unblock concern is structurally addressed** — file-processor `(unhealthy)` becomes `(healthy)` for the first time since the P0-03 trade-off in March 2026.

## §7. Risks + mitigations

1. **SW1 Docker-stack-in-CI flakiness** (NOVEL pattern). Mitigation: minimal subset compose (backend + postgres + redis + caddy + temporal + file-processor only — skip Elasticsearch/MinIO/etc. unneeded for visual audit); explicit `--wait` on `docker compose up`; conservative timeouts; retry-on-failure step pattern from `reusable-e2e-tests.yml`.

2. **SW2 (z) sub-discovery** — Temporal listening on 0.0.0.0 may have additional config requirements (CORS for UI, frontend Service binding). Mitigation: SW2 runs `docker compose up -d temporal` first, validates UI on :8233 + gRPC on :7233 from another container via `docker exec`. If sub-issue surfaces, document + fall back to next-best path (e.g. host network if rebind alone doesn't work).

3. **SW3 /dashboard surfaces 10+ violations**. Mitigation: Q3 +3h+ expansion budget; fix critical (axe weight 10) inline only; defer serious to /dashboard own-wave with explicit list; defer cosmetic always. Honest framing in audit if budget exhausted before all critical fixed.

4. **SW4 cross-browser audit + 7 routes × 5 violations each = 35+ findings**. Mitigation: triage by axe weight; W139 closes critical only; serious + cosmetic batched into "a11y per-page wave arc" carry-forward (similar to Schedule W61-W74 14-wave polish arc precedent per `feedback_planning_estimates.md`).

5. **SW5 LHCI gate ratchet variance > 0.04 per-run** (per W124 SW4 finding). Mitigation: 3-session × 3-run = 9 measurements per URL (W124 SW4 methodology); if variance still > 0.05, leave gate at current value + document for W140+.

6. **SW7 polish-pass surfaces W138 audit-claim drift** (W138 Lesson #9 — already happened mid-W139 with W122 §Honesty correction!). Mitigation: dedicated polish-pass invariant table comparing against W137 + W138 polish-pass tables; document any drift findings honestly.

7. **Temporal rebind surfaces an actual security regression** that I'm misjudging (e.g. Docker network isolation isn't as airtight as I assume). Mitigation: SW2 includes explicit threat model in commit message — Docker `internal` network is bridge-mode without external publish; only services on the network can reach Temporal; same posture as Postgres/Redis. If a security review later disagrees, can revert + pivot to mTLS sidecar option or back to `--ip 127.0.0.1` accept-as-dev-limit.

8. **W138 Lesson #2 (z) Path resurfaces in W139** — additional unanticipated structural surprises (e.g. visual-audit.yml needs different action permissions, RS256 keypair generation differs on ubuntu-latest, TIME_WAIT exhaustion on heavy parallel routes). Mitigation: include "(z) something we haven't thought of" as explicit hypothesis path in SW1+SW3 investigation; budget +3h+ explicit per Q3.
